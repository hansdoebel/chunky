# Hugging Face dataset snapshots

Open **Window → Datasets** in the Mac app. Search a public dataset name or topic (for example, `BeIR/scifact`), select a result, then choose a configuration/split and sample budget (or the legacy row limit). Review the linked dataset card and license before downloading.

The default destination is `~/Downloads/Chunky Datasets`. **Choose folder…** remembers another destination using a security-scoped bookmark. **Use default folder** restores the default for future downloads; neither operation moves or deletes existing snapshots.

Each download creates a unique directory with `rows.jsonl` and `manifest.json`. The manifest records the Hub dataset ID, full immutable revision, configuration, split, license, source link, timestamp, actual/total rows, requested limits, and SHA-256 of the JSONL bytes. Every Dataset Viewer page must report the selected Hub revision in `X-Revision`; a changed, absent or mismatched revision stops the download. Search again to select the current revision. This avoids mixed-revision exports; historical revisions are not fetched through the Viewer.

Downloads take the first complete rows, not a random or representative sample. Legacy row samples retain the 10,000-row / 50 MiB limits; byte-budget samples use the limits described below. Every HTTP response is capped at 5 MiB. A page that contains truncated cells is rejected. Cancellation or a failed request leaves no completed snapshot. Existing files are never overwritten. Private/gated datasets and datasets without Dataset Viewer support are unavailable in this version. The app does not execute remote dataset scripts or download media URLs embedded in rows.

Use the saved folder as the source for the [dataset benchmark and test-collection workflow](dataset-benchmarks.md). Corpus text, queries and relevance judgments often live in separate configurations or repositories; downloading a corpus does not manufacture relevance labels or produce retrieval-quality results. The dataset library itself never changes embedding settings or Qdrant collections.

## Validation

Unit fixtures cover paging, immutable revision checks, incomplete/truncated responses, bounds, cancellation, snapshot integrity and saved folder selection. macOS UI captures use fixture metadata rather than claims of measured benchmark performance. A live read-only API probe verified public search, dataset metadata and the `X-Revision` header on `BeIR/scifact`; no model inference or retrieval-quality benchmark is implied.

## Wikipedia choices and sample budgets

The library recommends four public sources: **Mini Wikipedia · English passages** (`rag-datasets/rag-mini-wikipedia`, `text-corpus/passages`), **Simple English Wikipedia** (`wikimedia/wikipedia`, `20231101.simple/train`), **English Wikipedia** (`20231101.en/train`) and **German Wikipedia** (`20231101.de/train`). Simple English is a different edition, not a smaller random English sample. The mini corpus is a useful starting point for a small test cluster, but does not guarantee that vectors and indexes fit its capacity. Wikimedia sources report CC BY-SA 3.0 / GFDL; the mini corpus reports CC BY 3.0. Review each linked card and retain attribution.

**Small**, **Medium** and **Large** cap saved JSONL at **10 MiB**, **100 MiB** and **1 GiB**, respectively. These download the first complete rows until the next row would exceed the byte budget, the source ends, or one million rows have been saved. They do not download full Wikipedia. The final result shows actual rows, bytes and stop reason. A single row exceeding the budget fails without saving; rows are never silently skipped or truncated. Individual rows and HTTP responses remain limited to 5 MiB. Oversized pages retry with fewer rows. The destination must have the selected budget plus 64 MiB free space before a download starts. Cancellation or failure removes staging files; existing snapshots remain untouched.

The displayed **full split compressed Parquet size** comes from revision-checked Hugging Face metadata. It is not the JSONL sample size, network transfer size, or Qdrant capacity. Missing/partial/unverifiable metadata is shown as unavailable and does not invent a size. Legacy row samples may show an approximate JSONL estimate based on the first 20 complete rows; article lengths vary and HTTP metadata adds overhead. Cloud capacity is checked separately during import because embeddings and indexes consume additional storage.

**Legacy row sample (benchmark-compatible)** retains the original 10,000-row / 50 MiB workflow and schema v1. Byte-budget downloads use schema v2 with the budget, row ceiling and stop reason. The Benchmark window also accepts v2 snapshots when their actual size is at most 50 MiB and their row count is at most 10,000. Benchmark additionally validates the selected text field: at most 1,000 rows, 32 KiB per row and 8 MiB total, with no silent truncation. A small snapshot can still contain Wikipedia articles above those text limits. Use the separate **Window → Dataset Cloud Ingest** workflow for larger snapshots or longer text; that workflow chunks text with explicit provenance.

Large snapshots are validated off the UI actor with bounded file reads, a complete SHA-256 check, JSONL validation and retained SHA-256 digests for fixed 64 KiB blocks. Ingestion re-verifies each block before emitting complete rows, preventing changed bytes from being consumed after preflight. A changed later block stops ingestion; any previously imported verified rows are handled by the Cloud workflow’s explicit partial-collection policy.

Read-only research on 2026-11-17 verified all four Viewer configurations, licenses and revisions. Wikimedia revision `b04c8d1ceb2f5cd4588862100d08de323dccfbaa` reported English 6,407,814 rows / 11,630,929,031 compressed bytes, German 2,845,308 / 5,771,317,942, and Simple English 241,787 / 156,885,218. Mini revision `1f9f3b53fbc5995b85aab8e993504ad42c5f16f6` reported 3,200 / 797,357. These are historical research observations; the UI fetches current verified metadata instead of hardcoding them. English/German first-100-row probes returned complete, untruncated rows under the response cap. No embedding benchmark or capacity guarantee is implied.

## Pre-embedded DBpedia option

The fifth recommendation is the official Qdrant source `Qdrant/dbpedia-entities-openai3-text-embedding-3-small-1536-100K`, `default/train`. Read-only research verified revision `0d5fd00fbc5a9c0c836d70cd409f7e461255e572`, 100,000 rows and 1,650,651,517 compressed Parquet bytes. Its source card does not declare a license; the UI reports that honestly and links the card.

Rows are saved unchanged. The correct vector column is `text-embedding-3-small-1536-embedding`, with `combined_text` as input. A separate legacy `openai` column also has 1536 dimensions but different values: matching dimensions do not establish model compatibility. Use the Cloud ingest workflow’s pinned profile and an OpenAI-compatible gateway serving **text-embedding-3-small at 1536 dimensions** for query embedding. The library does not select a vector column, convert vectors, or mutate embedding settings. A future source revision is not automatically considered compatible with that pinned profile.
